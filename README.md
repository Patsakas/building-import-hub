# Building Import Hub

A buildings registry: people sign in, see their buildings and import them from an Excel file. The
app was generated with [Lovable](https://lovable.dev) and then made production-ready without taking
it out of Lovable: business users can keep building in Lovable while every change goes through the
same automated checks before it reaches production.

**Production:** https://building-import-hub-prod.web.app ·
**Staging:** https://building-import-hub-staging.web.app ·
**Write-up:** [`docs/WRITEUP.md`](docs/WRITEUP.md) (SSR decision, deployment choices, issues and
fixes, and the [guardrail demos](https://github.com/Patsakas/building-import-hub/pulls?q=label%3Aguardrail-demo):
deliberately broken pull requests that CI stopped)

## Architecture

```
Browser ──► Firebase Hosting          static SPA (TanStack Start, SPA mode, no SSR)
   │
   ├──► Supabase Auth                 email + password, no public sign-up
   ├──► Supabase Data API (PostgREST) reads, protected by Row Level Security
   └──► Edge Function import-buildings
             verifies the user's JWT, parses the Excel file, validates every row and inserts
             all rows or none, through a client scoped to that user (RLS applies)
```

There is no application server. Server-side code lives in Supabase Edge Functions, and the
frontend is plain static files, so it runs on Firebase Hosting's free plan.

| Path                                  | What it is                                                         |
| ------------------------------------- | ------------------------------------------------------------------ |
| `src/`                                | The app (file-based routes in `src/routes`)                        |
| `src/integrations/supabase/`          | Generated by Lovable: do not edit                                  |
| `supabase/migrations/`                | SQL applied to the deployed environments                           |
| `drizzle/migrations/`                 | The same SQL, applied by Lovable to its own backend                |
| `supabase/functions/import-buildings` | Edge Function, its parser and unit tests                           |
| `supabase/tests/`                     | pgTAP tests (RLS, privileges) and Edge Function integration tests  |
| `e2e/`                                | Playwright tests of the UI                                         |
| `scripts/`                            | Deno scripts: template generator, CI guardrails, user provisioning |
| `.github/workflows/`                  | CI, Deploy, and the main → lovable sync                            |
| `AGENTS.md`                           | Rules for Lovable and other AI agents working in this repo         |
| `docs/RUNBOOK.md`                     | Deploys, rollbacks, user accounts, credentials, troubleshooting    |

## Local development

Prerequisites: [Bun](https://bun.sh) 1.4, Node 24, Docker, and [Deno](https://deno.com) 2 to run
the Edge Function tests.

```sh
bun install
npx supabase start            # local Postgres, Auth, Edge Functions; applies migrations + seed.sql
npx supabase status -o env    # shows API_URL and PUBLISHABLE_KEY for the next step
```

Point the app at the local stack in `.env.local` (git-ignored; it overrides the committed `.env`,
which belongs to Lovable):

```sh
VITE_SUPABASE_URL=http://127.0.0.1:54321
VITE_SUPABASE_PUBLISHABLE_KEY=<PUBLISHABLE_KEY>
```

```sh
bun run dev
```

Sign in as `alice@test.local` or `bob@test.local`, password `password123`. These seed users exist
only in the local stack.

## Checks

CI (`.github/workflows/ci.yml`) runs on every pull request and every push to `main` and `lovable`.
`main` only accepts pull requests with all three jobs green.

- **Frontend:** Prettier, ESLint (which forbids `createServerFn`), TypeScript, Vitest and the build.
  The build must be a static site with an empty server function manifest, must not contain a
  server-side secret (a secret key, a `service_role` JWT or a private key), and gets a Content
  Security Policy computed from its own inline scripts (`scripts/csp.ts`), which the end-to-end
  tests run under.
- **Edge Functions:** `deno lint`, `deno check` and `deno test` for every function, with frozen
  lockfiles.
- **Database and integration:** migrations identical in `drizzle/` and `supabase/`; a fresh
  Supabase stack; pgTAP tests for RLS, table privileges and schema-wide guardrails; integration
  tests of the Edge Function and the auth settings; Playwright end-to-end tests.

Run the fast ones locally:

```sh
bun run format:check && bun run lint && bun run typecheck && bun run test && bun run build
npx supabase test db
deno test --config supabase/functions/import-buildings/deno.json \
  --allow-read=public supabase/functions/import-buildings
```

The integration and end-to-end tests need the local stack: see `supabase/tests/functions` and
`e2e/README.md`.

## Environments and delivery

```
Lovable ──sync──► lovable ──PR + CI──► main ──release vX.Y.Z + approval──► production
                     ▲                   │ │
                     └── Sync workflow ──┘ └──every merge──► staging
```

| Environment | Frontend                               | Backend                                | Deployed by                                |
| ----------- | -------------------------------------- | -------------------------------------- | ------------------------------------------ |
| Lovable     | Lovable preview                        | Lovable's built-in backend             | Lovable                                    |
| Local       | `bun run dev`                          | `npx supabase start`                   | you                                        |
| CI          | build + Firebase Hosting emulator      | Supabase stack in the runner           | every pull request and push                |
| Staging     | Firebase `building-import-hub-staging` | Supabase `building-import-hub-staging` | every merge to `main`                      |
| Production  | Firebase `building-import-hub-prod`    | Supabase `building-import-hub-prod`    | a published GitHub release, after approval |

Staging is a copy of production on the same services, so it catches what a local stack cannot:
Supabase's hosted bundler and API permissions, the real auth settings, and migrations applied to a
database that already holds data. A release is cut from a `main` commit that is already live on
staging.

The Deploy workflow re-runs the whole CI suite on the commit, then: checks the access
token's permissions and that the environment's auth settings match `supabase/config.toml` (an
administrator applies those; the deploy token cannot change them), builds the frontend for that
environment (and verifies it does not point at Lovable's backend), so that a failed check or build
changes nothing, then applies the migrations, deploys the Edge Functions, deploys the frontend to
Firebase Hosting through Workload
Identity Federation (no stored Google keys) and smoke-tests the live site. Each environment's
configuration lives in its GitHub environment; see `docs/RUNBOOK.md`.

## Working with Lovable

Lovable edits and syncs the **`lovable`** branch (in Lovable: _Project → GitHub → branch_). Its
changes reach `main` through a pull request, so they get the same checks and review as anything
else. After every merge to `main`, a workflow merges `main` back into `lovable`, so people building
in Lovable always start from the latest reviewed code.

`AGENTS.md` gives Lovable's AI the rules of this repo (no server code, Edge Functions for server
logic, RLS on every table, migrations mirrored in both folders, no secrets), and CI enforces them.
